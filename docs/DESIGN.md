# Rally: Monte Style — design decisions

Moved from the claude.ai "Road Rally" Project. The app was first delivered as a claude.ai artifact; this repository is now the source of truth.

## Scope
- Reads photos of the Route Instruction pages into a table of Route Instructions, merges by RI, and sorts.
- User-visible text calls both the source pages and the app's table Route Instructions; RI means only a single Route Instruction; never Route Table, RT, RIs, or route information.
- Adds VM and TT columns. OM and CZT are hidden on the Run screen.
- Prep: rally name, date, crew (driver, navigator, and passengers), vehicle (free text, optional; Crew and vehicle card; shown only on the set-up form), car number (CN), Class (A, B, C, or D; same line as OCF), OCF (always displayed with four decimals, e.g. 1.0100; the Data summary and the CSV do too), and the close-RI limit. Internet is allowed.
- Setup entry rules (each is checked when the field is committed, by leaving it or pressing Enter; a rejected entry shows its message and the field reverts to its previous value, so nothing is partly applied):
  - CN: blank or a whole number from 0 to 999; blank computes as 0 minutes. Otherwise "Car number must be a whole number from 0 to 999".
  - Close-RI limit: blank or a number from 0 to 5.0 vehicle miles. Blank is stored and shown as the 0.5 default; 0 flags only rows with identical VMs. Otherwise "Close RI limit must be between 0 and 5.0 miles".
  - OCF: a number greater than 0, shown to four decimals. Blank, 0, a negative number, or text is rejected with "OCF must be a positive number.".
- New from sample (Rallies tab): each tap creates a new rally from the built-in sample and opens set-up. Name "Sample Rally", today's date, CN 7, Class C, OCF 1.0100, vehicle "Rally Car", crew Jane Driver and John Navigator with no passengers, speedometer at its start value, the default close limit, no TA, nothing completed.
- Run: shows the first uncompleted RI. Small Undo button and a 58 px Complete button; Undo un-completes the last completed RI in RI order. No internet needed.

## Tabs and settings

**Rallies and navigation**
- The Rallies list shows the newest date first, then the most recently updated. A rally with no name shows as "Untitled rally". At the top of the tab are New rally, New from sample, and Load (see Storage → Rally files). Each rally has Open, Save, and Delete. Open goes to Run when the rally has Route Instructions and a name, otherwise to Setup. Labels are in sentence case.
- Tabs other than Rallies are disabled until a rally is open. The URL hash (`#setup`, `#route`, `#run`, `#data`) selects the tab. At start the app opens Run if the current rally has Route Instructions, otherwise Rallies.

**Setup**
- A new rally starts with today's date, an empty name and CN, OCF 1.0000, the speedometer at 35 mph, and the default close limit.
- Display (saved per device): Time format HH:MM:SS (default) or HH:MM.cc, and Theme Day (default) or Night. The Time format applies to CZT, TT, and estimates on screen and to the CSV time columns.

**Route editor**
- CZT accepts H:MM:SS(.s), H:MM.cc, and H:MM, with hours below 48; displayed times wrap at 24 h. Any other entry shows "CZT format: HH:MM:SS or HH:MM.cc" and reverts.
- An RI can't be blank or duplicate another RI; either shows a message and reverts. RI order is the number, then the suffix (12 < 12A < 13). An RI with no number sorts last.
- Add row gives the new row the next RI (last + 1, or last + "+" for a text RI) and copies the previous row's OM (0 after a restart). The first row added is "/0.00". Delete row and Clear Route Instructions each ask first.
- Clear Route Instructions is titled "Clear Route Instructions", its OK button says "Clear", and its text is: `Clear all n Route Instructions and their run data from “<rally name>”? This cannot be undone.` With exactly one row it reads `Clear the 1 Route Instruction and its run data from “<rally name>”? This cannot be undone.` The rally name falls back to "this rally". It removes the rows, all Time Allowances, and the last-read highlight; completion marks and estimate locks go with the rows, and page copies and sign images no row uses any more are freed. The text says nothing about page photos or page images, and the action leaves the photos in place. The button is disabled when the rally has no Route Instructions, and is enabled again once a row is added, pasted, or read.
- Dialog wording avoids contractions (for example "cannot", not "can't").
- Page photos (add, remove, Clear photos) are per rally and session-only; see Reading pages → Page photos.
- Sign images and the Page control (see Reading pages → Sign images): under a row that has `[sign: …]` tags or sign images, a read-only copy of its instruction with each tag replaced by its image or shown as a placeholder (the same layout as Run); under every row with a band, a Page control (a small button labelled "Page") that opens the row's band full screen. Tap a sign image to see it full screen (as on Run). The editor never adds, changes, or removes an image. A row with no band shows no Page control; rows added by hand or pasted as CSV have no band and no images, and their tags show as placeholders (and are flagged: see Page image flags).
- Page image flags (listed with the other flags, each starting `RI n:` so the row highlights): `RI n: check page image` when a band needs checking: the reader's `y` fell in a different band than its `row` (`y` decided on a page in doubt; `row` kept on a sound page), `y` fell in no band, the band is the fallback, or the band was built from `row` alone because the page was sideways; `RI a–b, c, d–e: check page images` once for a page whose headings the page cross-check moved (it lists the rows whose band is still on that page copy, plus rows read from it and left with no band, as runs in route order, which is table order, not RI number order; a run is written `a–b` with an en dash, a single row alone, runs separated by `, `, and one unbroken run is `RI a–b`; a row a partial Re-read moved to a new page copy is no longer listed, so the flag names no row that has no problem; no truncation, and it is one flag; the labels are the rows' current RI labels; all of its rows highlight, and they get no per-row flag); and `RI n: page image missing` when the row has a band but its page copy is gone (Re-read restores it). A row read from a page that ends up with no band is flagged `RI n: check page image` as well (alone, or inside the page flag's range when the page has one), and highlights. A row with a band and `[sign: …]` tags but no graphic found gets no flag of its own. When at least two rows on one page copy have tags and none of them got a sign image, `RI a–b, c: no sign images found` is listed once (the tagged rows, in the same run form: an untagged row between two of them breaks a run), and those rows highlight. The flag is worked out from the rows whenever the flags are listed and is not stored: it goes away when a Re-read finds sign images or the tags are edited out. Rows with no band are not counted. Rows whose `y` fall in the same band are all flagged `RI n: check page image` (a missing rule can merge two rows into one band, and the first row's `row` and `y` then agree).
- Sign-count flag, for a row with no band and no `imgCheck` (typed, pasted, or loaded from a rally file) whose instruction has `[sign: …]` tags: `RI n: k of m sign images` when it has k (1 or more) sign images and m tags and k differs from m, or `RI n: no sign images` when it has none. Only sign images that are stored on the device count, and the flag is not worked out until the stored images are known. A row with no tags gets no flag, whatever images it has (they follow the text). Rows with a band or `imgCheck` keep the flags above and never get this one. Like every flag it is derived from the rows each time and never stored, starts with `RI n:` so the row highlights, and counts toward the cap of 8 below.
- Flags above the table: an RI with no OM, an OM less than the RI before it (missed restart?), a CZT earlier than the previous CZT, and rows out of order. The first 8 are listed, then "…and n more". Rows from the last read are highlighted.

**Data**
- "Run data" means completion marks, Time Allowances, and estimate locks.
- Clear run data and Remove saved API key each ask first (Delete rally asks first too, from the Rallies list).
- Clear run data is titled "Clear run data", its OK button says "Clear", and its text is: `Clear the run data for “<rally name>”? The Route Instructions stay. This cannot be undone.` The rally name falls back to "this rally".
- Delete (a button on each rally in the Rallies list) is titled "Delete rally", its OK button says "Delete", and its text is: `Delete “<rally name>” and all its data from this device? This cannot be undone. Save it to a file first if you want to keep it.` It also drops the rally's page photos and frees its page copies and sign images. Deleting a rally that is not open leaves the open rally open; deleting the open rally closes it and stays on the list. Rows returned by a read of that rally that is still running are discarded, with no message. The rally name falls back to "Untitled rally".
- The Data tab's controls are the summary, Download CSV, Download JSON, Copy CSV, the App section (install note, Remove saved API key, version), and Clear run data. Delete rally, Duplicate rally, Import JSON, and Copy JSON are not on it: Delete is on the Rallies list, and Save and Load replace the rest (Duplicate: Save, then Load with Keep both, which keeps the sign images; Clear run data runs a route again).
- Page images line, for the open rally: `Page images: n pages, x.x MB on this device` (`1 page` in the singular), `Page images: none; sign images x.x MB` when its rows refer to sign images but no page copy (as after loading a rally file), or `Page images: none`. `n` counts the page copies the rally's rows refer to; the size is the stored size of those copies and the rally's sign images. Delete row, Re-read, and Clear Route Instructions can lower it.

**Dialogs**
- Tapping outside a dialog closes it without change. Esc closes no dialog; it only cancels a speedometer edit.

## Computation
- VM = OM × OCF.
- The first row starts the first leg. Each later restart (OM printed "x.xx/0.00") starts a new leg at VM 0 and TA 0. The first row need not be printed "/0.00", because pages may be read in any order; there is no check or warning on it. There is no separate leg for rows before the first restart: they are in leg 1, with VM = OM × OCF in the printed frame. A leg is identified by the RI of its first row.
- A bare "/0.00" OM is a restart at OM 0.00. This is how a rally's start RI is printed. It is accepted wherever OMs are read: row entry, CSV paste, and the reading prompt.
- Row entry of an OM accepts only blank, a number (x.xx), a restart (x.xx/0.00), or a bare restart (/0.00). Any other entry, such as 5/3, is rejected with "OM format: x.xx, x.xx/0.00, or /0.00", and the row's OM and Rst stay as they were.
- A row with no OM (for example the finish RI) shows no VM and no estimate, and shows a TT only if it has a CZT. It is skipped when checking close rows and can be completed like any other row. When the active RI has no OM and no CZT, the active card says "no OM, so no VM or estimate".
- TT = CZT + CN minutes + TA.
- TA is the Time Allowance (SCCA term). It is never negative and is stored in whole seconds (0 to 90:00).
- TA (confirmed by the owner): a TA entered on a row applies from that row through the row before the next restart. Rows before it keep their TT, and a restart starts at TA 0. A later TA in the same leg replaces the earlier one from its own row on. The app stores TA as events {ri, ta, at}.
- Renaming an RI moves its TA events to the new RI. Deleting a row removes its TA events; Clear Route Instructions removes all TA events and completion marks.
- Estimator (confirmed by the owner): estimated TT = TT of the nearest earlier row in the same leg that has both a TT and a VM + ΔVM ÷ speedometer mph. A row with a TT but no VM is skipped. A negative ΔVM counts as 0. ΔVM and the speedometer are both in vehicle units, so the OCF is accounted for.
- Estimates are always shown (≈, italic) in the TT column of every row without a CZT, wherever an earlier TT exists in the leg. Nothing to tap.
- Locking: an estimate is locked only when its RI is completed; it then ignores later speedometer and TA changes. Un-completing releases it. No lock symbol.
- Speedometer: saved with each rally (reloading keeps it, and a blank value is never saved or reset on load). A new rally starts at 35 mph.
- Close rows: adjacent rows whose VM gap is ≤ the per-rally limit (Setup; default 0.5 vehicle miles) are highlighted in the VM cell. Across a restart the gap runs to the previous frame's end. The active card shows "NEXT IN x.xx".
- No system clock or sensor feeds any computation. Each RI's completion time is logged for post-event analysis and as a backup record of checkpoint passage if the Richta app misses one. It is exported in the CSV. No logged time feeds VM, TT, TA, Undo, or estimates.

## Run controls
- One strip: a TA button on the left (reads "TA m:ss", for example "TA 0:00" or "TA 1:05"; highlighted when non-zero) and the speedometer on the right (−5 −1 [mph] +1 +5, limit 1–100 mph; a blank entry is invalid, like any value outside 1–100: it shows "Speedometer must be between 1 and 100 mph" and reverts).
- TA dialog, titled "Time Allowance": a big entry field, ±5, ±15, and ±60 s buttons, and Zero. Changes are pending until Set; Cancel or tapping outside leaves TA unchanged. The minus buttons stop at 0:00.
- TA entry: m:ss (seconds 0–59) or bare whole seconds; a leading + is tolerated and a blank entry is 0. A negative entry, decimal minutes, fractional seconds, or seconds of 60 or more in m:ss are rejected with "TA: seconds (90) or m:ss (1:05)" (a negative one says "TA cannot be negative"), and the dialog stays open. The limit is 90:00 ("TA is limited to 90:00"). TA is always shown as m:ss, whatever the Time format; TT, CZT, and estimates follow the Time format.
- Direct entry: tapping a field selects its value. Enter or Set commits; for the speedometer, tapping away or Esc leaves the value unchanged.
- Full screen (⛶ in the header): asks the browser for full screen where allowed, and always hides the app's header and tabs. A small ✕ (top right) exits.
- Sign images on Run: the instruction of the active card and of every row in the Run list shows its sign images in place (see Reading pages → Sign images): each `[sign: …]` tag is replaced by its image when the row has as many images as tags, in order; otherwise no tag is replaced and the images follow the text. A tag with no image is a muted placeholder box (dashed border, muted colour, the tag's words). Images are small: at most 44 px tall in the list, 76 px on the card (22 px in short landscape, where images that follow the text sit on the same line), never wider than the instruction. The active card also has a Page control ("Page", in the card header) that opens the row's whole band full screen; a row with no band has none. The whole-row band image is not shown inline anywhere. Complete and the run controls stay fully visible, at all three layouts, for a row with no images, one inline image, two images, images that follow the text, and a placeholder. These are defaults that the Run screen sizing work (#5) may tune.
- Tap a sign image, or the Page control, to see it full screen, fitted on a dark background. A tap anywhere closes it. It changes no run state, and Complete cannot be pressed while it is open. A missing or failed image never blocks running, completing, or Undo.
- Night theme dims sign images and the full-screen view to about 60% brightness. They are never inverted.
- Images have no effect on VM, TT, TA, restarts, estimates, or close rows.
- Scrolling: the list keeps the user's scroll position through every change. The app scrolls only when Complete is pressed, or when a rally's Run tab is first shown in a session; both place the active RI near the top with one row above it. A rally with no active RI (no Route Instructions, or all complete) starts at the top on its first visit. Each rally keeps its own scroll position, in memory only.
- Undo is disabled when nothing is complete. Un-completing shows "RI n marked not complete".
- When every RI is complete, the active card reads "All n Route Instructions complete" with Undo last complete. With no Route Instructions, the Run tab shows "No Route Instructions yet." and a Build it on Route button.
- Run layout: in landscape at 640 px or wider, the Run list uses two columns and shows the CP column; otherwise it uses one column and no CP column.
- The screen is kept awake while the Run tab is shown.
- Leaving the browser's full screen (for example with Esc) also leaves the app's full-screen mode.

## Storage
- Saved on the device (localStorage) after every change.
- Rallies are stored only on the device. There is no account or cloud copy.
- localStorage keys are `rallyMonteStyle.v1` (rallies) and `rallyMonteStyle.apikey` (the API key). The earlier `rallyRT.v1` and `rallyRT.apikey` keys are deleted unread on load; there is no migration.
- Rallies saved without Vehicle (in localStorage or JSON files) load with it empty; there is no migration.
- Page copies (see Reading pages → Page images) are stored in IndexedDB, not localStorage. On the first save of a page copy the app calls `navigator.storage.persist()`; a refusal is silently accepted. Sign images (see Reading pages → Sign images) are stored there too, as separate records. Rallies saved before page images existed have no bands and show no images, and rows read before sign images existed have no sign images; there is no migration (Re-read upgrades a row).
- Page images are not in a rally file, CSV, or any other export. Download JSON (support use, until #88 replaces it) writes the rally as stored, so it includes each row's bands, `signs` ids, and `imgCheck`, but no image data; it cannot be loaded back. A rally file holds no bands, page copies, or `imgCheck`, and carries sign images.
- Export: the rally file (see Rally files below) is the only round-trip format. CSV is an export-only report (augmented Route Instructions with class, close limit, and estimate lock status); its details block includes a Vehicle line after the crew lines, written even when empty.
- If the browser refuses to save on the device, a banner says so.
- Download JSON is `{app: 'rally-monte-style', version: 1, rally: {…}}`, the stored rally as is. There is no JSON import: a JSON file given to Load is refused with "That is an earlier version’s JSON export, which this version cannot load."
- CSV format: details lines Rally, Date, Driver, Navigator, Passengers ("; " separated), Vehicle, Car number, Class, OCF, Close RI limit (mi), and Speedometer (est.), with OCF written to four decimals (e.g. 1.0100); a blank line; then the columns RI, Restart, OM, VM, CZT, TA (s, whole seconds), TA entered here, TT, Est TT, Est locked, Done, Done at, CP, Instruction, and Info. A restart's OM is written x.xx/0.00 and its VM prev/0.00. Time columns follow the Time format setting.
- Exports: Download CSV, Download JSON, and Copy CSV. File names are "<date> <name>", with each run of characters other than a letter, digit, `_`, `.`, or `-` replaced by a single `_`; Save adds `.rally`.
- An absent `cls` or `closeMi` on a stored rally means "no class" and the default close limit (0.5); a rally the user has not edited stores neither.
- Stored image ids: `pg…` is a page copy and `sg…` is a sign image. The prefix is functional: the Data line counts as pages only the ids that do not start with `sg`. Sign images are kept, shown, and counted for any row that has `signs`, with or without a band.

**Rally files** (format: `docs/RALLY-FILE.md`; this section is the app's behaviour)
- A rally file is a zip with the extension `.rally` that holds one rally: the Setup fields (not the theme, time format, or model), the Route Instructions with their sign images (no page information), and the run state (each RI's complete mark, completion time, `ttDone`, and estimate lock, and the Time Allowances). It never holds page photos, page copies, bands (`src`, `check`, `pageCheck`), `imgCheck`, the model, read or parsing data, or the API key. `created` and `updated` are not written and are set to the load time.
- Save (a button on each rally in the Rallies list) writes the rally with `kind: "saved"`, named like the CSV and JSON files plus `.rally`, entries stored (no compression), sign images as `signs/0001.jpg` and so on in the order met. A sign image that is missing from the device is left out of its row. Where `navigator.canShare({files})` is true, Save opens the system share sheet; cancelling it (`AbortError`) saves nothing and shows no message. Any other share failure, and every device that cannot share the file, downloads it (anchor and blob URL) and shows "Saved <name>". The Blob type is `application/octet-stream`, so no browser renames the file to `.zip`. A TA for an RI that is not in the rally is not written.
- Load (on the Rallies tab) opens a file input with no `accept` filter (iOS Safari mishandles extension filters). The file is recognised by its contents, not its name. If the device cannot save (the storage banner is showing), Load is refused with that banner's text. A file over 50 MB is refused, before it is read, with "That file is over 50 MB, so it was not read."
- A file with a broken structure is refused with "Rally file not loaded" and a message naming the reason, and nothing on the device changes; the reasons are listed in `docs/RALLY-FILE.md`. Anything else is a content problem: the file loads, the value is left blank, dropped, or defaulted, and one notice lists what changed, by RI. A JSON file gets its own message (an earlier version's JSON export).
- Content problems and their handling: a value that fails the rule for typing it by hand (CN, OCF, close limit, speedometer, class, date, OM, CZT, TA) is left blank or at its default; a sign image whose path is missing from the zip, or that is not a readable JPEG or PNG, is dropped; a missing or blank `ri` keeps the row with no RI; a duplicate RI keeps the first row and drops the later ones; a missing instruction loads blank; a TA for an unknown RI, a second TA for one RI, or an invalid TA is dropped; an unknown `kind` opens Setup. The row order of the file is kept. Rows go through the same `normRow` as rows from pages, so a loaded row never has a band or `imgCheck`; the page-based checks do not apply, and a row whose sign images do not match its tags gets the sign-count flag.
- The load notice: a clean load shows a toast `Loaded “<name>”`. A load with problems shows an OK-only dialog titled "Rally file loaded", for example `Loaded “X”. 2 sign images could not be read (RI 16, RI 25). 1 value was left blank (RI 40 OM).` (an RI is named once per kind of problem; problems are grouped as sign images, blank values, rows with no RI, duplicate RIs, dropped Time Allowances, and an unknown kind).
- Sign images from a file are stored as separate IndexedDB records with new `sg` ids. An image over 800 px on the long side is scaled to 800 px and stored as JPEG 0.85; a smaller one is stored as it is. Each new id is pending (see Reading pages → Page images) until the rally is saved, then released and `gcPages` runs, on success and on failure, so a load that fails part way leaves no image behind and no image of a loaded rally is freed at the next start.
- Same rally: when the file's `rally.id` matches a rally on the device, the app asks, in a dialog titled "Rally already loaded": `“<name>” is already on this device. Replace it with the file, or keep both?` with Replace, Keep both, and Cancel. Replace keeps the `id`, replaces the rally's data, clears its last-read highlight and Run scroll position, keeps its session page photos, and frees images it no longer uses; rows returned by a read of that rally that was still running are discarded, with no message, and that photo goes back to the state it had before the read. Keep both gives the loaded copy a new `id` and adds " (2)" to its name (" (3)" and so on if taken; a rally with no name becomes "Untitled rally (2)"). Cancel changes nothing. With no `id`, or no match, the file loads as a new rally with no question (an `id` in the file that matches nothing is kept, so the rally can be replaced later by loading the same file again). An `id` that is not 1–64 letters, digits, `_`, or `-` (first a letter or digit) is ignored.
- After a load the rally is current. `kind: "saved"` opens Run; `"distributed"`, a missing `kind`, or an unknown `kind` opens Setup. Run state in a distributed file is loaded as written.
- No network is needed to Save or Load.
## Getting the Route Instructions in
- Add page photos → Read. Reading needs an Anthropic API key, entered on the Route tab (see Reading pages). With no key, Read explains this. API errors say whether the network or the key failed.
- A copied photo can be pasted on the Route tab where the device allows it.
- Add page photos opens a picker that accepts several images at once, so a whole rally can be added in one go.
- Paste rows accepts CSV only: an app CSV, with the rally details (including the Vehicle line) above the `RI,…` header line skipped, or any CSV with a header line that has the same column names. It reads the RI, OM (a `x.xx/0.00` or bare `/0.00` OM marks a restart), CZT, CP, Instruction, and Info columns by header name, and ignores the computed columns. Completion marks and TA entries are not restored; a rally file is the full record. Text with no header line, such as pasted JSON or prose, finds no rows.
- Paste rows with no rows found shows "No rows found in that text", keeps the dialog open, and leaves the table unchanged.

## Testing
- The core is pure (no DOM, no clock) and is unit-tested under Node.
- Playwright runs at 390 and 360 px portrait and 844 px landscape. These are the supported layouts.
- `pwa.py` covers photo read and merge by RI on the API-key path, including a rally switch while a read is running.
- Vision (`src/vision.js`: orientation, band finding, perspective correction, sign graphics) is pure (pixels in, numbers out) and is unit-tested under Node in `test/vision.test.js`, which CI runs. The test draws a synthetic ruled page from invented content (not scanned: `test/synth.js`), with row heights varying about 10:1, and photographs it with perspective (about 10% keystone, both ways), slant of ±3°, a shadow gradient, a dark and a light background, blur, compression, and all together, plus a faint full-height scanner streak and a ruled map box above the headings. Expected values come from the geometry drawn, never from current output. Cases: every band holds its own row, within a few pixels, and is not flagged; the page copy is portrait and at most 2,000 px; a page turned 90° (the pre-pass) and 180° (`y` mapping), and `rotation` 90 or 270 (`y` ignored, bands from `row`, every row flagged); invalid `rotation` is 0; `y` in no band, `y` over `row` on a page in doubt (a majority of rows disagree, and a `row` that names no band), one row's `y` a row off on a sound page (`row` kept, `src` `rules`, flagged), an adjacent block of rows off, just under half off (`row` wins) against exactly half and just over half (`y` wins), a row rule missing in the lower half (`y` wins below the merge, the merged rows flagged) and in the upper half (most rows lie below the merge, so the cross-check moves the headings: the page flag, and every row gets `check` and `pageCheck`), the S26 pattern (the two top rows' `y` one row too low: both keep their `row` bands and are flagged, and the third row stays flagged by the same-band rule), `row` alone, too few rules (fallback), missing or invalid `row` and `y`, a continuation row at the top; the page cross-check (a decoy band above the headings, and a photo cut off above the first rule found); a rule missing from the photo, which puts two rows in one band (both flagged); the first rows above the first rule found (with a `y`: a fallback band, flagged; with no `y`: no band); the image flags in `test/core.test.js` (a row with no band is flagged, and the page flag's range includes it at the start, in the middle, and at the end of the page; a partial Re-read: a row moved to a new page copy in the middle splits the run, at the start or end shrinks it, a row returned with no valid band stays, a single remaining row prints alone; a row with a band has no `imgCheck`, in `normRow`, `mergeRows`, and `dropStaleImgCheck` on load; the sign flag's runs); the whole sheet kept (a map above and the foot below the table are inside the copy, and the table is a rectangle in it); `src` values; signs: a diamond with a plaque, a bordered white rectangle with text, and a noisy photo-like block are found and merged correctly, two side by side are two images ordered left to right, at most as many images as tags, a row with no tags is not searched, multi-line text and a row with tags but no graphic give no false positives, a cell with one line of text and a sign on a clean page gives no misses. The Instruction cell is found from the right edge: with one column rule left of Instruction missing or too faint to find, every tagged row gets the same sign boxes as the full page; with another number of columns left of Instruction (4, 5, and 9 rules in all), signs are found; with fewer than 3 column rules there are no sign boxes and no error.
- The table frame (`gridOf`) is also tested on rules built from the geometry drawn (exact numbers) and on a drawn and photographed page with a ruled box as wide as the table above the headings. Cases: column rules of mixed heights, some reaching up into the box (all kept, the frame starts at the headings, the box lines are not rows); a column rule short of the body by under and over half a row pitch, at the top and at the bottom; a row rule spanning exactly 80% of the width (a row rule) and just under (not); a 90% row rule that stops short of an Instruction rule by more than half a column width (not) and by less (a row rule); column ends jittered by a few pixels, top and bottom independently (same columns and frame); a ruled box below the table with one interior column rule running on into it (the bottom limit stays at the last row's rule); a photo cut off through a row at the top and at the bottom (every interior rule covers the first or last rule found, so it is the limit); a box line under half a pitch above the headings' top rule and one under half a pitch below the last row's rule, with the column rules ending at the table's rules (the limits stay at the table's rules); interior column rules reaching a box above, one exactly to its top line and one to its other line: 2 of 5 cover the box line, all 5 the headings' top rule, which is the top limit; no majority (three interior rules cover the upper rows, three the lower): neither limit snaps, reported, and the half-length columns are not column rules; a vertical beside the table (dropped, one second run); a slanted column rule broken into two pieces that overlap by more than the trace joins (one rule), two parallel pieces farther apart than the merge distance (not combined), a piece and a streak that does not line up (not combined); a full-width line near the image's bottom edge with no box (not counted with the box lines); too few rules (no frame, no error).
- Sign-image layout (`Core.signParts`), the band and sign fields, merge, and freeing are unit-tested in `test/core.test.js`. `images.py` covers the screens: inline sign images at the three layouts, images after the text when the counts differ, placeholders, the Page control, and the lifecycle (edit, Delete row, Clear, Re-read, Save and Load of a rally file with Keep both, Replace, and Cancel, a file with no id, a file with content problems, rejected files, a failed image store, Delete rally), and the `RI a–b: no sign images found` flag (listed once, tagged rows highlight, cleared by editing the tags out), and a partial Re-read (no banded row has `imgCheck`, and the old copy's page flag no longer names the moved row). The flag derivation is unit-tested in `test/core.test.js` (two or more tagged rows with no image give one flag with the right runs, an untagged row between them breaking a run; one gives none; a page with an image gives none; rows with no band are ignored; editing the tags out clears it). The mock reader's canned rows carry `row` and `y` (and tags in their instructions); e2e checks select rows by property (has a band, has no band, tallest band, one sign, two signs), not by RI number.
- The rally file format is pure (`src/rallyfile.js`: zip read and write, encode, decode, validation, the load notice) and is unit-tested under Node in `test/rallyfile.test.js`, which CI runs: every rejection and content case in `docs/RALLY-FILE.md`, the field mapping, unknown fields ignored, a save-then-load round trip with `Core.compute` identical before and after, and a file built by hand from the spec alone and deflated by a zip tool (`test/fixtures/hand-built.rally`, with its sources beside it). The entry parsers (CN, OCF, close limit, speedometer, OM) and the sign-count flag are tested in `test/core.test.js`. `rallyfile.py` covers the Rallies and Data tabs, Save (download, share sheet, cancelling, failure), Load (storage that cannot save, over 50 MB, the hand-built file, `kind`), and Delete on the list.
- Orientation is tested through the browser's own decode: `images.py` feeds JPEGs carrying each EXIF orientation (1–8), and sideways pixels with no rotation tag, through the photo picker, and each must give the same bands and sign images as the upright file. Tests never apply EXIF orientation themselves. The upright page (about 2400×3960, above the 2,000 px page-copy limit, flat) is drawn in the browser with asymmetric signs and Pillow writes every file, `o1` included, through one JPEG encoding; `o1` is the reference, and each other file must give the same rows with bands, the same sign count per row, and crops within a pixel tolerance (mean absolute grey-level difference at 64×64 of at most 12; the noise between the fixtures is about 8, and the same measure on `o1`'s crops against mirrored and quarter-turned copies of themselves is at least 24, so a mirror or rotation bug fails it).
- Thresholds were tuned on real phone photos and scanned Route Instruction pages kept outside the repository.
- A guard test checks that the built page makes no claude.ai artifact-runtime calls.
- The tests use the built-in invented sample rally, "Sample Rally" (`src/sample.js`); mocks of the page reader return invented canned rows of their own.

## Reading pages
- Pages are read with the user's Anthropic API key, entered on the Route tab and stored only in that device's local storage. It is never exported or committed. The Data tab can remove it. Only a key that starts with `sk-ant-` is saved; any other entry is rejected with a message and nothing is stored.
- Model picker (saved per device): Sonnet 5.5 (default, about 2¢/page), Haiku 5.5 (about 0.1¢/page), Opus 5.5 (about 7¢/page). The cost notes assume Nov 2026 list prices and an image of about 3,900 tokens. Pages are sent at up to 2,000 px.
- Orientation: before a page is sent, the app counts its long horizontal and vertical rules; if vertical rules outnumber horizontal ones, the page was shot sideways and is turned 90° clockwise to portrait (either direction is fine; the reader's `rotation` fixes upside-down). The sent image is that turned page, not corrected in any other way.
- A note the reader returns for a row is appended to its Info as ' [OCR: …]'.
- The reader returns two more fields per row, before `note`: `row`, the row's position counting the ruled rows below the column headings from 1 (a continued part at the top of the page counts as a row but is not returned; the prompt says so), and `y`, the row's vertical centre as a fraction of image height (0 top, 1 bottom, two decimals). `row` is used only if it is a positive integer and `y` only if it is a number from 0 to 1; a missing or invalid value is ignored and is never an error. `y` is measured on the image exactly as sent (after the pre-pass turn). The raw `row` and `y` are not stored.
- The reader also returns a page-level `rotation`: the clockwise degrees the image as sent must be turned for its text to read upright (0 or 180 normally). The reply is the JSON object `{"rotation": …, "rows": […]}`; a bare array of rows still reads, as rotation 0. A missing or invalid `rotation` (anything but 0, 90, 180, or 270) is 0. For 180 the app turns the page copy 180° and uses 1 − `y` for every row on the page. For 90 or 270 (the pre-pass missed) it turns the copy upright, ignores `y` on that page, builds bands from `row` alone, and flags every row on the page.
- Sign graphics and photos in an instruction are written `[sign: …]` in its place, giving the sign's words exactly, or a short description if it has none (for example `CHECKPOINT at [sign: deer crossing]`).
**Page images**
- For each page read, the app saves on the device (IndexedDB) the page copy as JPEG at quality 0.85: the whole sheet after the orientation turns, with its perspective corrected as one page so that the table is a rectangle, at most 2,000 px on the long side. Content outside the table (a map above the headings, notes below it) is kept, because the original photo is not (a strong keystone limits the copy to half a table width beside the table and 0.6 table heights above and below it, and to what the photo shows; the background around the sheet may be in it). It is not the exact image sent. Page photos themselves stay session-only.
- Finding the table (pure, in `src/vision.js`; thresholds are in its `K` block):
  - The image is thresholded locally: ink is darker than the local mean (a window of 1/40 of the page width) by 12 grey levels, so shadow and the background around the page do not swamp the rules.
  - A rule is a long dark stroke, followed across short breaks (where another rule meets it) and fitted as a line or a gentle curve. It must be darker than the paper on both sides, which rejects page edges, background, and shadow edges. A column rule has a contrast with its own paper of at least half the typical column rule's, which rejects scanner streaks, and must cover the table's body (below). A row rule in the body must span at least 80% of the table width and cross both rules that bound the Instruction cell. Rules closer together than 0.5% of the page height are merged.
  - The body runs from the headings' top rule to the last row's bottom rule. Its limits are set by the interior column rules (those between the two outer ones): the top limit is the outermost row rule that spans the table (at least 80% of its width) and is covered by most of them (more than half), and the bottom limit is the same from below. An interior column rule covers a row rule when it is present at its height, or when that row rule is the nearest candidate to the column rule's end within half the median row pitch; a line the column rule neither reaches nor ends nearest to is not covered, so a box line close to the headings' top rule (or to the last row's bottom rule) is not selected by column rules that end at the table's rules. A plurality never sets a limit, so a few column rules that reach into a box above or below cannot select its line, while column rules that reach past the table still cover the headings' top rule or the last row's bottom rule. Row pitch is only a unit for tolerances; rows are not assumed evenly spaced. A side where no row rule is covered by most of them is not guessed: that limit falls back to the outermost row rule on that side that passes the row test (and still meets the interior column rules); the app reports it as not snapped. A photo cut off through a row is not this case: every interior column rule covers the first rule found, so it is the limit. A frame is refused only when too few rules are found (fewer than three column rules or two row rules).
  - A column rule covers the body when it reaches from the top limit to the bottom limit, falling short by at most half the row pitch at each end. Any part above the body is ignored, so a rule that reaches up into a box above the table is kept. Pieces of one column rule that the trace left apart (a break, or an overlap longer than the trace joins) count as one rule when they overlap or leave a gap of at most half a row pitch, their fitted lines are within the merge distance (0.5% of the page height) of each other over that stretch, their union covers the body, and the combined rule passes the same darkness and contrast tests; two parallel pieces farther apart than the merge distance, or a piece and a streak that does not line up with it, are not combined. A row rule crosses the Instruction cell's two rules (the second-to-last and third-to-last column rules, counted from the right as the sign step does) when it reaches each to within half the median column width.
  - The first outer column rules, the table width, and the pitch are provisional, because a vertical beside the table would widen it. The column test and row test run twice, never more: the second time always uses the final pitch (re-measured from the body's row rules) and any fallback limit; when the outer rules that survive the first column test differ from the first look's, the second run starts again from the candidate rows instead. Box lines outside the body (a row-rule candidate outside the body's limits that spans at least 80% of the table width between the outer column rules, is as dark as the body's rules by the same half-the-typical-contrast test, and is reached, within half a row pitch, by both outer column rules as traced before clipping, so a line near the image's edge with no box is not one) are listed apart from the rows, so they can be counted and are never rows or bands.
  - The table frame is the outer column rules and the body's top and bottom limits, so a box above the headings or below the last row is outside it, and a vertical streak joined to one interior rule does not move a limit, because a limit is the rule covered by most interior column rules. Box lines outside the body are not rows or bands. The photo is warped so that the frame is a rectangle, and the rules are found again in the corrected table (with a small margin), so bands and graphics are exact; they are then reported as fractions of the page copy. Each row's `y` goes through the same correction (at the table's horizontal centre).
  - The headings band is the body's first band; anything above it, such as a map in a ruled box, is outside the frame. Row n is the nth band below the headings.
  - Page cross-check: the headings offset (a headings band above the first rule found counts, for a photo cut off at the top) that puts the most rows' `y` inside their own band is found. If it has at least two rows in agreement, more than the rule-based offset, and differs from it, it is used, the page gets one flag, and every row of the page gets `check: true` and `pageCheck: true`.
  - Sound page: a page is **sound** when all three hold: (a) the cross-check did not move the headings; (b) more than half of the page's rows with a usable `y` (valid and inside the page copy) have that `y` inside their own `row`'s band, where a `y` in no band disagrees, rows with no `y` are left out, and exactly half is not a majority (`K.SOUND_MAJORITY`, a fraction, not tuned to the evaluation set); (c) every row read from the page has a `row` that names a band, which catches a row rule missing low (two rows merge into one band, every `row` below it names the band one too low, and the last `row` names no band). Otherwise the page is in doubt. A continued part at the top of the page counts as a row (the reader does not return it), so the first returned row's `row` still names its band and (c) is not affected. Sound or in doubt is worked out on every read, including Re-read, and is not stored.
- Band for a row, cropped from the Instruction column's left rule to the table's right edge (Instruction and Info), with its `src`: `rules` (the band from `row`, with `y` agreeing; or `y` fell in no band, which flags it; or `y` fell in a different band than `row` on a sound page, where `row` decided and it is flagged; two or more rows whose `y` fall in the same band flag all of them); `y` (`y` fell in a different band than `row` on a page in doubt, and decided, flagged; `y` is the `src` only on a page in doubt); `fallback` (too few rules found, or neither `row` nor `y` names a band: centred on `y` with a margin of 4% of the page height, flagged; clipped to the page copy, not to the window the rules were found in, so a row above the first rule found, or below the last, still gets one); `row` (built from `row` alone: `y` missing or invalid, not flagged; or the page was sideways, flagged). With no usable `row` and no `y` inside the page copy, the row has no band and no image, and it is flagged (see Page image flags).
- The rally record stores each row's band as `{page, top, bottom, left, right, src}`: the page copy id and fractions (0–1, four decimals) of the page copy, and how it was found, plus `check: true` when the `RI n: check page image` flag applies and `pageCheck: true` when the page flag does (both survive a reload). A row read from a page but left with no band stores `imgCheck`, the page copy's id, on the row itself, which is what flags it and puts it in the page flag's list; a rally file never holds it. A row with a band never has `imgCheck`; one left from an earlier read is dropped when the rally loads. Bands read before `src` existed have none. An RI split across a page break gets one band, from the page its RI number is on.
- At startup, once the stored images are listed and only if localStorage loaded, page copies and sign images no row refers to are freed (for example after a crash during a read). Images saved by a read that has not yet merged are never freed.
- A page copy exists only while at least one row's band refers to it. Delete row, Re-read, Clear Route Instructions, and Delete rally free copies no longer used. Clear photos and removing a photo do not touch page copies.
- Editing a row's text, or renaming its RI, leaves its band and sign images unchanged.
- Re-read: a returned row with a valid band replaces the old row's band and sign images (with none, if no graphic was found), and the old page copy and images are freed if no row still uses them. A returned row with no valid band keeps the old row's band and sign images (the image shows what is printed for that RI, whatever the reader made of the text). Rows not returned keep their band, images, and copy.
- If saving a page copy fails, the read still succeeds and its rows are saved without bands or sign images. The "Pages read" summary adds `Page images could not be saved on this device; rows from this page have no image.`
- If a row has a band but its page copy is missing, the row shows no Page control and Route lists `RI n: page image missing`. There is no message on the Run tab. A sign image that is missing is left out, and the row lays out its tags as if it had fewer images.
**Sign images**
- Sign images are cropped from the original photo after its EXIF orientation is applied, the same oriented image the page copy is made from. Every read of the original photo goes through that one oriented decode.
- Only rows whose instruction contains `[sign: …]` are searched, and only inside the row's Instruction cell (between the Instruction column's left and right rules, a few pixels clear of the rules).
- The Instruction cell is located by counting column rules from the right: the table's right edge, then the Instruction column's right and left rules (the Instruction column is second to last; Additional Info is last). This is the same count the band step uses for the band's left edge. At least three column rules are needed; the total is not fixed, so a table that lost a column rule left of Instruction, or has another number of columns, still gets its sign images. With fewer, the page's rows get no sign images (their bands keep their fallback).
- Text height is measured once per page, across all its Instruction cells (never per cell: on a clean page a cell may hold one line of text and a sign), from the lines of text in them: ink is joined sideways (not between lines), and only pieces at least 1.5 times wider than tall count. The most common height, each piece weighted by its width, finds the text; pieces under half of it (lettering inside a sign) are dropped; the text height is the 40th percentile of the rest, by width, so lettering inside a sign does not set it.
- A graphic is a piece taller than 1.8 and wider than 1.2 times the text height. Boxes that touch or nearly touch merge, so a sign stays with its plaque and a photo stays in one piece. At most as many graphics as the row has tags are kept, the largest first, then ordered top to bottom, then left to right.
- Each graphic is cut from the original photo at full resolution through the same perspective correction as the page copy, at most 800 px on the long side, stored in IndexedDB as JPEG 0.85, and kept on the row as `signs`, the ordered list of image ids. Rows read before sign images existed have none.
- Display, on Route and Run: if the number of images equals the number of `[sign: …]` tags, each tag is replaced by its image, in order, with the tag's words as the image's alt text; otherwise no tag is replaced and the images, if any, follow the text. A tag that is not replaced is a muted placeholder box with the tag's words. A row with a band but no sign images shows only the Page control; a row with a band and tags but no graphic found shows placeholders and has no flag of its own (the page flag in the Page image flags bullet applies when two or more tagged rows on a page copy all get none); a row with no band gets the sign-count flag instead.
- The whole-row band image is not shown inline. The Page control, on the Route row and on the Run card, opens it full screen.
- Lifecycle: sign images stay with the row when its text is edited (placement follows the counts). Re-read replaces them, or keeps them with the old band. Delete row, Clear Route Instructions, and Delete rally free them. A rally file carries them (see Rally files), and Download JSON carries their ids only. The Data tab's Page images size includes them.
- Reader replies: the rows are found as a JSON array (bare, or as the `rows` of the reply object) even with prose around it and [brackets] in instruction text, and several fenced blocks are combined. A fenced block that isn't JSON is skipped, and the rows from the valid blocks are used. A reply with no valid block finds no rows.
- Each page thumbnail shows the model that read it last. Every page that has been read offers "Re-read", which reads that page again with the currently selected model. Each row it returns replaces the row with the same RI and other rows stay, so a row misread on an earlier read stays until it is deleted in the Route editor.
- Errors name the cause: no network, key rejected (401), refused (402/403: credit or model access), or reply cut off.
**Page photos**
- Page photos belong to the rally they were added to. The Route tab shows only the open rally's photos. Opening another rally neither shows nor clears them; they are there again when that rally is reopened.
- Photos are session-only: a reload or app restart drops them, because the Route Instructions read from them are saved. To Re-read after a reload, add the photos again.
- Each thumbnail has a ✕ that removes only that photo, after a confirm. The dialog is titled "Remove photo", its OK button says "Remove", and its text is: `Remove this page photo? Route Instructions already read from it stay.`
- Clear photos is titled "Clear photos", its OK button says "Clear", and its text is: `Clear all n page photos from “<rally name>”? Route Instructions already read from them stay.` With exactly one photo it reads `Clear the 1 page photo from “<rally name>”? Route Instructions already read from it stay.` The rally name falls back to "this rally". The button appears only when the open rally has photos.
- Neither ✕ nor Clear photos changes Route Instructions, Time Allowances, completion marks, or the last-read highlight.
- Delete rally drops the rally's photos. Removing a photo, Clear photos, and Delete rally free the photos' object URLs.
- Read and Re-read record the owning rally when they start. The rows they return merge by RI into that rally, and that rally's last-read highlight is updated, even if another rally is open when the read finishes; the open rally is untouched. The last-read highlight and the reading state are kept per rally, so reads on different rallies can run at the same time.
- When a read finishes while another rally is open, the "Pages read" summary names the owning rally (`“<rally name>”: …`); when the owning rally is open the text is unchanged.
- Open item: run a full 18-page rally through all three models once and compare against the paper.
